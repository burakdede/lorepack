# Windows resident observer diagnostics

Issue #801 tracks the Windows failure retained from PR #800 at `adb86563`:
five accepted RSS reports followed by 813 ms without another accepted report.
The reader had no observed exit or signal. This does not establish why reporting
stopped.

The later Windows verification at `4f0cbe74` failed a different workload:
`parser-versions.test.ts`, `depends on a parser that contributed nothing to this
project`. The reader delivered four reports, then no accepted report for 435 ms,
with no observed exit or signal. That test had no diagnostic trace. Only this
case now enables the existing Windows flag around its unchanged two builds and
assertion, restoring the prior environment on every exit. Its parser-version
reset, input files and scheduling remain unchanged. This reporting loss has no
established shared cause with the original rule-semantics failure. Trace results
are diagnostic evidence, not final P01 performance qualification.

Strict Node-only validation also exposed a pre-existing fixture type mismatch:
the parser-version workbook supplied an array where the fixture writer expects
raw XML text. Explicit `.toString()` preserves the writer's existing implicit
array coercion. The unchanged writer generated byte-identical complete workbook
buffers before and after this coercion, without clock overrides. This is a
fixture typing correction, not a parser change.

The original rule-semantics regression enables the internal
`LOREPACK_OBSERVER_DIAGNOSTIC=1` setting on Windows. The observer records up to
16 fixed-field events for reader emission, parent receipt, watchdog execution
and reader closure. Reader and parent elapsed times use separate clocks;
ordering across the two pipes is not a total event order. Instrumentation may
affect scheduling.

On an observer failure, the existing error includes the current snapshot.
Reader closure writes one final bounded stderr snapshot so queued diagnostic
events remain visible after test error serialization. Healthy shutdown emits
no final snapshot. The trace contains no source text, paths, arguments or raw
reader stderr.

The diagnostic preserves numeric RSS stdout, 100 ms sampling, the 250 ms
reporting deadline, 5000 ms startup deadline, output caps and fail-closed parser
termination. It does not retry, wait for closure or extend a parser lifetime.

A separate D247 Ubuntu verification failure exposed an early timer callback:
the reporting watchdog declared silence at 249.951 ms, before its 250 ms
deadline. Both watchdogs now check monotonic elapsed time in the pending-I/O
phase and, if early, schedule only the rounded-up remainder. A new report or
stop cancels that pending timer. This corrects premature expiry; it does not
explain the Windows reporting or startup stalls.

Run the affected parser checks with:

```sh
pnpm exec vitest run --project parsers packages/parsers/test/windows_resident_memory.test.ts packages/parsers/test/resident_memory.test.ts packages/parsers/test/isolation.test.ts
```

The mocked reader checks actual silence, typed failure, cleanup, bounded late
events and healthy shutdown. The Windows-only real PowerShell case blocks the
parent for 800 ms while the reader samples normally, then checks queued report
delivery. It is skipped on other platforms because they use a different
observer. A passing diagnostic regression alone does not explain the historical
failure or close #801. Fresh native execution and causal evidence remain required.

## Startup observation

The later Windows small benchmark at `e75d74e7` failed before the first valid
sample: 5001 ms, no observed reader exit or signal, and zero buffered stdout
characters. Its actual CI merge, `3c59e0d`, has the same tree as `e75d74e7`.
This startup failure and the earlier reporting gap have no established shared
cause. An empty parent buffer does not locate a delay in the reader or parent.

The optional trace also records the reader's parent-observed spawn event,
startup watchdog arm/fire/check, and fixed first-iteration PowerShell milestones:
script entry, refresh returned, RSS read, and before the first stdout write.
Entry precedes process lookup. Milestones use the existing 16-event ring and
final failure snapshot; healthy shutdown still emits no diagnostic line.
The first-sample barrier, numeric stdout and all timing/output limits remain.
Missing or separately delivered markers are inconclusive. The entry marker
follows error-preference and Stopwatch initialization, so it cannot time that
setup or the earlier process startup interval.

The existing benchmark measurement step enables this flag only on Windows;
its commands, corpus, sample counts and scheduling stay intact. Windows timing
reports from this instrumented step are diagnostic evidence, not final
performance qualification. Final performance evidence requires an unchanged
workload without observer instrumentation. No successful replay by itself
explains either historical failure.

The mocked startup control checks silence through the original 5000 ms deadline,
then typed failure and parser/reader termination, bounded late markers and final
closure. It does not execute PowerShell or establish a native failure mechanism.
The existing real PowerShell stall case awaits readiness before stalling and
therefore checks reporting after startup, not startup queue delivery.

## POSIX reader failures

Issue #801 also retains two distinct acceptance failures from PR #800 head
`4f0cbe74`. Ubuntu aborted a `/proc/<pid>/smaps_rollup` read with a timeout cause
during the setup build for `lifecycle/diff-reads-builds-not-sources`. macOS
reported a `SIGKILL` reader exit during the first build for
`mixed/every-format-contributes-with-its-own-provenance`. Each native suite had
163 passes, one failure and four existing skips. The logs do not establish
elapsed read time, why a read was late, or who killed the macOS reader.

POSIX failures now add a structured context message around the original error,
preserving that error as `cause`. It contains the platform, initial or subsequent
sample phase, monotonic elapsed milliseconds, reader PID, exit code, signal,
local kill-request state and an allow-listed abort reason name. The context
contains no paths or arbitrary error text. The original cause chain remains
available separately. Successful reads produce no diagnostic output and add no
timer or process. These failure-only fields do not require the Windows diagnostic
flag, since the native acceptance failures do not enable it.

The macOS `localKillRequested` field reports Node's `ChildProcess.killed` state.
It does not identify the sender of a signal or prove that the spawn timeout
caused a termination. The original 250 ms POSIX query deadline, 100 ms sample
interval, output limits, parser budgets and fail-closed result remain intact.

The diagnostic-contract regression uses controlled reader failures to verify
context and original cause retention, and checks intentional-stop cancellation.
Its controlled 249.95 ms value verifies numeric capture only; it does not
reproduce a native premature POSIX abort. Run it with the original real reader
and parser-isolation tests:

```sh
pnpm exec vitest run packages/parsers/test/posix_resident_memory.test.ts packages/parsers/test/mac_resident_memory.test.ts packages/parsers/test/linux_resident_memory.test.ts packages/parsers/test/resident_memory.test.ts packages/parsers/test/windows_resident_memory.test.ts packages/parsers/test/isolation.test.ts
```

This is diagnostic preparation, not a causal correction of the retained native
reader failures. Fresh native evidence and a demonstrated mechanism are still
required before #801 can close.

On macOS with Node 24.21.0 and pnpm 11.18.0, the unchanged implementation failed
five diagnostic-context assertions and passed the intentional-stop case. After
the wrapper, all six passed. The original affected six-file suite passed 82
cases with two existing native-Windows skips; architecture checks passed 305
cases. Strict Node-only test typing, project types, lint, format, build and release
policy checks passed. The controlled failure tests verify context retention and
fail-closed behavior; they do not explain either historical native POSIX failure.
